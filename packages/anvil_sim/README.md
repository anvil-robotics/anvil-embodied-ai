# anvil-sim

Validates the Anvil `ee_abs`/`ee_rel` training + closed-loop evaluation
pipeline (`anvil_trainer`, `anvil_shared.ee_transform`, `ee_runtime`) against
LeRobot's LIBERO benchmark, using the public `lerobot/libero` dataset.

Three comparison arms, derived from the same LIBERO task's episodes
(`task_index=10`, "put the bowl on the plate", `libero_goal` suite /
internal `task_id=8` — the two numbering schemes differ, see
`libero_convert.py`):

- **A. native** — LIBERO's own 7-dim delta action (Δxyz + Δaxis-angle +
  gripper), unmodified. Zero Anvil code: plain `lerobot-train` /
  `lerobot-eval --env.type=libero` against the Hub dataset directly.
- **B. ee_abs** — Anvil's 10-dim rot6d absolute EE pose, derived from the
  dataset's own observed trajectory (act-from-obs) via
  `anvil_shared.ee_transform`.
- **C. ee_rel** — Anvil's 10-dim rot6d SE(3)-relative EE pose (UMI-style,
  `T_rel = inv(T_state) @ T_action`), via `ee_rel_forward`/`ee_rel_inverse`.

B/C reuse the exact production `anvil_trainer`/`ee_transform`/`ee_runtime`
code paths — this is a real pipeline validation, not a lookalike. Instead of
a custom gym env, B/C plug into `lerobot_eval.py::rollout()`'s
`env_preprocessor`/`env_postprocessor` hooks so all three arms share the
same underlying `LiberoEnv`.

## The validation harness: verify a new treatment in 3 steps

The primary product of this package is a **gated validation pipeline** that
lets you test any new policy idea / data treatment / action representation
with minimum effort — and makes it structurally impossible to burn a full
training run on a config whose eval path is broken (the failure mode that
cost this project four separate full sweeps before the harness existed).

**Step 1 — write one spec YAML** under `packages/anvil_sim/src/anvil_sim/studies/libero_ee/configs/` (see the 14
existing files there for every supported pattern):

```yaml
# packages/anvil_sim/src/anvil_sim/studies/libero_ee/configs/task10_my_idea_act.yaml
name: task10-my-idea-act
task_index: 10
env_suite: libero_goal
env_task_id: 8
dataset_group: goalabs        # or a new group you add to libero_convert.py
train:
  trainer: anvil-trainer
  action_type: ee_abs
  policy_type: act
  steps: 50000
eval:
  action_type: zerocal_goal_abs
  control_mode: relative      # illegal pairings are rejected at load time
```

**Step 2 — (only if your treatment introduces new math)** add the dataset
construction to `libero_convert.py`, the eval decode to
`libero_processor.py`, and a real-data identity check to
`bench_runner._MATH_VALIDATORS`. Unit-test the round trip.

**Step 3 — run it**:

```bash
uv run --package anvil-sim anvil-sim-bench run packages/anvil_sim/src/anvil_sim/studies/libero_ee/configs/task10_my_idea_act.yaml
```

The pipeline executes eight idempotent stages — `convert → validate-math →
dataset-validate → gt-replay → smoke → train → eval → record` — where every
cheap check runs BEFORE training. The `gt-replay` stage is the hard gate
that catches eval-path bugs unit tests can't see: it replays the dataset's
own ground-truth actions through your exact eval processor chain
(`anvil-libero-replay`, no policy involved) and must land within
`gates.gt_replay_margin` (default 15 pc points) of the native replay
baseline. If the ground truth can't succeed through your eval path, no
checkpoint ever will — the run aborts in minutes with a per-step trace to
diagnose, instead of failing silently after a 35-minute training run.

Results append automatically to `outputs/bench/results.json` and the
regenerated `outputs/bench/RESULTS.md` — no hand-maintained tables. Check
`anvil-sim-bench status` any time. Re-running a spec skips already-passed
stages (`--from-stage` / `--force-stage` to override).

For ad-hoc diagnosis outside the pipeline: `anvil-libero-replay` (GT replay
of any dataset/action-type/mode combination) and `anvil-eval-libero
--trace-dir=...` (per-step JSONL of raw policy output vs recovered native
command vs live state).

## Status (early 3-arm snapshot — superseded)

> This section is the original 3-arm milestone. It has since been extended by
> the goal-target family (Experiment 7), two more eval-path bugs (#4 gripper /
> Experiment 8, #5 chunk-anchor leak / Experiment 9), and a second task
> (Experiment 3c). The **ledger of record is `outputs/bench/RESULTS.md`**
> (regenerated by `anvil-sim-bench`); read Experiments 8–9 below for the
> current numbers. Kept here for the reasoning trail.

Core goal reached: all three arms (native / ee_abs / ee_rel) train with both
ACT and Diffusion Policy and run closed-loop in sim, with three real bugs
found and fixed along the way. Final results (50k steps ACT / 30k steps
Diffusion, 10-episode closed-loop eval each) — naming below factors each arm
into `{Abs|Rel}-{rotation encoding}-{translation frame}`:

| Arm | Name | ACT | Diffusion |
|---|---|---|---|
| native | `Rel-axis_angle-world` | 80% | 100% |
| ee_abs | `Abs-rot6d-world` | 40% | 50% |
| ee_rel | `Rel-rot6d-hand` | 30% (0% → 10% after bug #2, → 30% after bug #5) | 10% (was 0% before bug #2 below) |

`ee_rel` still trails `ee_abs`/native, but both independent policy
architectures converge on the same 10% after the fix, which reads as "this
representation is intrinsically harder to learn at this step/data budget"
rather than another lurking bug (an actual remaining bug would be unlikely to
give ACT and Diffusion the exact same number). The pipeline-correctness goal
is met; the two experiments below investigate *why* `ee_abs`/`ee_rel` trail
native — the first didn't reach a clean answer, the second did.

### Experiment 4: `ee_delta` / `Rel-rot6d-world` (calibrated) — not part of Anvil's contract

To test the hypothesis "rot6d rotation encoding is why ee_abs/ee_rel trail
native" (vs. the alternative hypothesis "the act-from-obs *absolute*-pose
formulation and, for ee_rel, body-frame relativization are the real cause"),
we added a 4th arm that keeps native's world-frame per-step delta formulation
exactly, swapping only the rotation encoding (axis-angle → rot6d). It lives
entirely in `anvil_sim` (`libero_convert.anvil_state_to_delta_action` /
`convert_episode_delta_actions`, `libero_processor.native_action_from_world_delta`,
`action_type="ee_delta"` in both processor steps) and reuses
`anvil-trainer --action-type=ee_abs` purely as a pass-through mechanism
(`EEAbsTransform` never touches `action`) — **it is not a real Anvil
contract**, just an ablation tool.

Result: **`ee_delta` ACT = 10%** — no better than `ee_rel`, worse than
`ee_abs`, contradicting the simple "swap the rotation encoding and it'll be
fine" prediction. Loss (0.033) and the actual computed normalizer stats
(checked directly from the checkpoint's
`policy_preprocessor_step_3_normalizer_processor.safetensors`) both looked
normal — no sign of an implementation bug. The likely explanation: `ee_delta`
accidentally removed the closed-loop correction both `ee_abs` and `ee_rel`
have. `native_action_from_targets` (used by both) always recomputes
`target_pos - current_pos` against the *fresh* current state every step, even
though the target itself came from a stale chunk observation — a
proportional-control-like self-correction. `ee_delta`'s action has no notion
of "target" to correct toward; it applies the predicted delta blind and
open-loop. Native gets away with the same open-loop replay because its delta
values are the simulator's own recorded commands (exact); `ee_delta`'s deltas
are reconstructed via `NATIVE_POS_SCALE`/`NATIVE_ROT_SCALE` (a *calibrated
approximation*, R²=0.92 for position but only R²=0.49 for rotation — see
below), so approximation error compounds unchecked over the open-loop chunk.
**This experiment accidentally varied two things at once (rotation encoding
+ presence of closed-loop correction) and doesn't cleanly isolate rot6d** —
the original hypothesis (absolute-pose formulation + body-frame
relativization, not rot6d itself) is not refuted, just not yet confirmed by
a clean ablation.

### Experiment 5: `native_rot6d` / `Rel-rot6d-world` (native-scale) — zero-calibration isolation

A cleaner follow-up: keep native's observation AND action values completely
unchanged (same 8-dim state, same controller-scale numbers straight from
`lerobot/libero`, zero calibration) and *only* re-encode the action's
rotation component as rot6d. `native_action_to_rot6d`
(`libero_convert.py`) treats native's raw rotation command numbers (NOT real
radians — that's the whole reason `NATIVE_ROT_SCALE` exists, to approximate
the unknown mapping from real angles to these numbers) formally as an
axis-angle vector, builds a rotation matrix, and flattens it to rot6d — an
exact, invertible re-encoding (`rot6d_action_to_native` is its precise
inverse, round-trip-tested), no physical-unit conversion, no approximation
error anywhere in the pipeline. Trains via plain `lerobot-train` (same path
as native, no anvil-trainer at all — `eval_native_rot6d.py` similarly reuses
lerobot's own stock `LiberoProcessorStep` for the observation side and only
swaps in a custom `NativeRot6dActionProcessorStep` for the action side).

Result: **`native_rot6d` ACT = 60%** — clearly below native (80%), clearly
above `ee_abs` (40%) and `ee_rel`/`ee_delta` (10%). Training loss (0.047)
was essentially identical to native's own (0.047), confirming this really is
an apples-to-apples comparison: the network finds the two encodings equally
easy to fit in the normalized-loss sense, yet closed-loop success still
drops ~20 points. **Conclusion: rot6d rotation encoding itself does cost
something — plausibly the `rot6d_to_matrix` Gram-Schmidt decode handling
regression error differently than axis-angle's direct 3-number output — but
it's a secondary effect (~20 points), not the dominant one.** The bulk of
`ee_abs`/`ee_rel`/`ee_delta`'s gap from native (40-70 points) is still
explained by the act-from-obs absolute-pose formulation, `ee_rel`'s
hand-frame rotation-position coupling, and (for `ee_delta`) calibrated
approximation replayed open-loop with no correction — not by rot6d itself.

### Experiment 6: zero-calibration re-run of ee_abs/ee_rel/ee_delta via `env.control_mode="absolute"`

Motivated by a hypothesis that `NATIVE_POS_SCALE`/`NATIVE_ROT_SCALE`
(rotation fit only R²=0.49) was corrupting *all* the ee_abs/ee_rel/ee_delta
comparisons, not just ee_delta. Confirmed by reading robosuite's OSC
controller source (`osc.py::set_goal`) that `env.control_mode="absolute"`
(`use_delta=False`) takes position in metres and orientation as an
axis-angle vector in radians **with zero scaling** ("No scaling of values
since these are absolute values" per the source comment) and no clipping
(`position_limits`/`orientation_limits` default to `None`) — so training
itself never touches `control_mode` (it's eval-only), meaning the existing
`ee_abs`/`ee_rel`/`ee_delta` checkpoints didn't need retraining, only a new
eval-time decoder (`absolute_native_action_from_target`,
`ZeroCalActionProcessorStep` in `libero_processor.py`, 4 modes) and
`--env.control_mode=absolute` instead of the old scaled-delta
reconstruction. One genuinely new arm was needed: `ee_rel_world` (SE(3)
relative, WORLD frame instead of hand frame — `anvil_trainer` gained
`ee_rel_world_forward`/`inverse` in `anvil_shared.ee_transform` and an
`EERelWorldTransform`, explicitly flagged experimental, not a stable
contract addition).

| Condition | Old (calibrated, `relative` mode) | New (zero-cal, `absolute` mode) |
|---|---|---|
| `Abs-rot6d-world` | 40% (`ee_abs`) | **20%** |
| `Rel-rot6d-world`, n-0 anchor (new) | — | **20%** |
| `Rel-rot6d-hand`, n-0 anchor | 10% (`ee_rel`) | **10%** |
| `Rel-rot6d-world`, n-(n-1) | 10% (`ee_delta`) | **10%** |

**Surprising result, opposite of the motivating hypothesis**: removing
calibration made `ee_abs` *worse* (40%→20%), not better, while `ee_rel`/
`ee_delta` didn't change at all. Since `ee_rel`/`ee_delta` are unchanged,
whatever limits them isn't the eval-time calibration step — it's the
checkpoint's learned predictions themselves (training-time issue, or an
inherent difficulty of those formulations, not something a better decoder
fixes). The `ee_abs` regression is unexplained so far; current working
hypothesis (**not yet verified**): robosuite's `relative` mode clips each
step's commanded displacement to `output_max=(0.05,...)` metres by default,
which may have been *accidentally* smoothing out noisy/incoherent
frame-to-frame absolute predictions; `absolute` mode has no such per-step
rate limit, so the same prediction noise could translate into more erratic,
less successful motion. Needs verification (e.g. inspecting eval videos for
visibly jerkier motion, or adding an equivalent rate limit to the
zero-cal absolute-mode decoder as a control) before treating this as
settled — flagged as follow-up work, not resolved by this experiment.

Answers to the 3 sub-questions this was meant to isolate (n=10 per cell,
small sample — a 1-episode difference is 10 points, so treat differences
below ~20 points cautiously):
- **Absolute vs relative** (`Abs-rot6d-world` vs `Rel-rot6d-world` n-0, both
  world-frame, both zero-cal): tied at 20% — this axis alone doesn't seem
  decisive once frame and calibration are controlled for.
- **World vs hand frame** (`Rel-rot6d-world` vs `Rel-rot6d-hand`, both n-0
  anchored, both zero-cal): world wins, 20% vs 10% — some support for the
  hand-frame rotation-position coupling hypothesis, but only a 1-episode
  margin.
- **n-0 anchored vs n-(n-1) consecutive** (both `Rel-rot6d-world`, zero-cal):
  n-0 wins, 20% vs 10% — some support for anchor+closed-loop over blind
  consecutive accumulation, again only a 1-episode margin.

### Experiment 7: unified `goal` target family — negative result

Motivated by a leftover concern in Experiment 6: `ee_abs`/`ee_rel` use
act-from-obs (`action[t] = encode(state[t+1])`), but `state[t+1]` is the
physically ACHIEVED next state (goal + impedance-controller tracking
error), not the commanded goal itself — a mismatch with how
`env.control_mode="absolute"` eval treats a policy's output (directly as a
goal). The plan was to define a single `G[t] = compose(state[t],
scale_action(native_delta[t]))` target and run all 5 control-variable
conditions (abs / world-n0 / hand-n0 / world-n(n-1) / hand-n(n-1)) through
it with `control_mode="absolute"`, so the controller's fixed scaling enters
once as a common factor and the n-0-vs-n-(n-1) comparison is clean.

**Two real bugs were found and fixed during implementation** (both
confirmed against real `lerobot/libero` episode data, not synthetic
numbers):

1. **v1 — wrong scale assumption (all 5 conditions: 0% pc_success).**
   `scale_action(d) = clip(d,-1,1) * output_max` (`output_max=[0.05]*3+
   [0.5]*3` from `robosuite/controllers/config/osc_pose.json`) was assumed
   to reconstruct the controller's exact internal target. Checking against
   real episodes: the true per-step displacement is only ~22% of that
   (fitted scale ≈0.011, not 0.05) — the impedance controller never fully
   reaches its internal aim point within one control step (normal OSC/PD
   behavior). Feeding the ~4.5x-too-large "goal" directly to
   `control_mode="absolute"` destabilized every rollout.

   Fix: `native_delta_to_goal` no longer scales at all — it composes
   `state[t] + native_delta[t]` PURELY FORMALLY (same trick as
   `native_action_to_rot6d`: treat the raw command numbers as if they were
   real units, with zero physical meaning attached). At eval time, a new
   function `recovered_delta_native_action` subtracts the REAL current
   state (not a stale anchor) from the reconstructed quantity to recover a
   native-delta-shaped 7-dim command, clips it to `[-1,1]`, and feeds it to
   `env.control_mode="relative"` — letting robosuite's own `scale_action`
   apply whatever the true physical scale is, so nothing here needs to
   guess it. `ZeroCalActionProcessorStep` gained a `deliver: "absolute" |
   "relative"` field (default `"absolute"`, so Experiment 6's 4 conditions
   are completely unaffected).

2. **v2 — world-seq/hand-seq built from consecutive formal goals (large
   constant offset, up to 0.94 in the wrong direction).** The first design
   built `world-n(n-1)`/`hand-n(n-1)` as the delta between consecutive
   `G[t-1] -> G[t]` (mirroring `ee_delta`'s shape but on formal goals). At
   eval time `ZeroCalActionProcessorStep`'s running-target accumulator
   resets to the REAL chunk-anchor state at every chunk start — but a
   goal-to-goal delta's own implicit anchor is the PREVIOUS GOAL, not a
   real state, so every chunk start introduced an offset roughly the size
   of `native_delta[0]` (empirically ~0.26) that never washed out. Separately,
   this delta family stores PHYSICAL displacement (metres/radians, like
   `ee_delta` already does), not the formal command-scale numbers — feeding
   it through `deliver="relative"` double-scales it (robosuite's
   `scale_action` would apply ANOTHER 0.05, empirically measured error 0.94,
   worse than bug #1).

   Fix: `world-n(n-1)` (condition #4) REUSES the existing `ee_delta`
   dataset/checkpoint unchanged — no new dataset or training needed for it.
   `hand-n(n-1)` (condition #5, the one genuinely new condition) is built by
   a new `convert_episode_delta_hand_actions` — the hand-frame analogue of
   `convert_episode_delta_actions`, using REAL consecutive states
   (`state[t] -> state[t+1]`), NOT the formal `goal_states` construction.
   Both conditions keep `deliver="absolute"` (matching Experiment 6 exactly
   — physical-unit targets go straight to `control_mode="absolute"` with
   zero further scaling).

After both fixes, all 5 conditions' recovery formulas were verified against
real episode data to floating-point-precision zero error before spending
any training compute.

**Results (ACT, task_index=10, 10 episodes)**:

| Condition | Dataset | `deliver` | pc_success |
|---|---|---|---|
| `abs` | `goalabs` (formal `state+delta`) | `relative` | **0%** |
| `world-n0` | `goalabs` | `relative` | **0%** |
| `hand-n0` | `goalabs` | `relative` | **0%** |
| `world-n(n-1)` | `delta` (existing `ee_delta`, reused) | `absolute` | **10%** (matches Exp. 6 exactly) |
| `hand-n(n-1)` | `delta-hand` (new) | `absolute` | **10%** |

Training loss for all 4 new checkpoints was unremarkable (0.034–0.037
train, comparable to `ee_delta`'s own 0.033) — not a training crash or a
silent stats-computation bug (`_force_rot6d_identity` was checked and ruled
out: it clamps rot6d dims to their already-natural `[-1,1]` range
regardless of whether the underlying rotation is near-identity, so it
behaves the same for `ee_abs`'s original targets and this experiment's).

~~**Core negative finding**: the 3 conditions built on the FORMAL
`state[t]+native_delta[t]` composition all get exactly 0% ... **the formal
composite goal itself is a target a network struggles to fit well enough
to close the loop**~~ — **THIS CONCLUSION WAS WRONG. See Experiment 8.**
The 0% had a mechanical eval-path cause (real bug #4, gripper semantics),
not a learnability cause. Kept struck-through rather than deleted so the
reasoning trail stays honest.

### Experiment 8: GT-replay diagnostic — bug #4 found, Experiment 7 conclusion REVERSED

To stop diagnosing surprising closed-loop numbers by guesswork, a new tool
was added: `anvil-libero-replay` (`eval_replay.py`) replays the DATASET'S
OWN ground-truth actions through the exact eval processor chain — no policy
involved. If the ground truth itself cannot succeed through a treatment's
eval path, no checkpoint ever will. (`LiberoEnv` resets to fixed per-task
init states tied to the reset index, so dataset episode k replays against a
near-matched initial condition — measured `init_state_pos_err` ~1–3 cm.)

On its FIRST run the tool caught **real bug #4**: the `goalabs` family
stores the gripper as LIBERO's native ±1 COMMAND (`native_delta_to_goal`
passes `native_delta7[6]` through), while `abs`/`rel`/`delta` store a
qpos-scale TARGET (~0.002–0.04). The delivery functions' bang-bang
comparator `abs(target) < abs(current_qpos)` is only meaningful for the
qpos convention — fed ±1 it is ALWAYS False, so **the gripper never closed
and every goalabs rollout failed at exactly 0% regardless of policy
quality.** All the float-precision offline validation missed it because it
compared only dims 0–8 (pos+rot), never the gripper against realistic qpos
values. Fix: `gripper_mode="native_cmd"` on the delivery functions /
`ZeroCalActionProcessorStep`, wired via the `zerocal_goal_{abs,world_n0,
hand_n0}` registry entries.

**GT-replay validation** (10 episodes, task_index=10):

| Replay path | pc_success |
|---|---|
| `native` (baseline ceiling for open-loop replay) | 60% |
| `goalabs` via relative delivery, BEFORE fix | 0% |
| `goalabs` via relative delivery, AFTER fix | **80%** |
| `goalabs` world-n0, AFTER fix | **80%** |

Replay after the fix exceeds the native baseline — expected: the recovery
step subtracts the LIVE state, giving GT replay a built-in drift correction
toward the demo trajectory that pure open-loop native replay lacks.

**Corrected Experiment 7 results** — the same checkpoints (training was
always correct; the bug was eval-only), re-evaluated in minutes with the
fixed path:

| Condition | Broken eval | Fixed eval |
|---|---|---|
| `abs` (formal goal, relative delivery) | 0% | **100%** |
| `world-n0` | 0% | **40%** |
| `hand-n0` | 0% | **30%** |

**`goal-abs` at 100% is the best ACT result in this entire benchmark —
above native's 80%.** The formal `state[t]+native_delta[t]` target with
recovered-delta relative-mode delivery is not merely learnable; it is (on
this task, n=10) the strongest formulation tested. Note the framing against
the action-space literature: this condition is an ABSOLUTE representation
with DELTA execution — the "delta beats absolute" comparisons conflate
representation with delivery, and this hybrid takes the best of both
(drift-correcting absolute target, controller-native delta command).

Two secondary replay findings, same session:

- The absolute-mode "undershoot" hypothesis from Experiment 6 is REFUTED:
  trace analysis of `delta`-family replay through `control_mode="absolute"`
  shows the arm moving 1.48x MORE than the demo per step (1.27 m vs 0.86 m
  path length) yet ending 0.675 m off-course — absolute delivery DIVERGES
  in open loop rather than lagging. Absolute-mode delivery is dynamically
  not equivalent to relative-mode delivery even with mathematically exact
  per-step targets; the controller-level mechanism remains open.
- `n-0` relativized variants read 40%/30% here — but that was itself an
  eval-path artifact (**bug #5**, Experiment 9 below): after resetting the
  chunk anchor per episode, `world-n0`/`hand-n0` both reach **80%** (native
  parity). The plain absolute goal (`goal-abs`, 100%) still leads, but
  anchor-relative re-encoding does NOT cost success on this task.

### Experiment 9: GT-replay at long horizon — bug #5 found, n-0 conditions REVERSED

Running the GT-replay diagnostic at the policy's real chunk horizon
(`--n-action-steps=100`, not the gate's default 1) surfaced **real bug #5**.
`world-n0` GT-replay scored **20%** where the forward/inverse identity
predicts parity with the `abs` condition (80%). The cause: the stateful eval
processors (`AnvilEEActionProcessorStep`, `ZeroCalActionProcessorStep`) track
the chunk boundary with a call counter and cache a per-chunk anchor, but
`rollout()` calls `policy.reset()` at every episode start (the policy replans
from episode-local step 0) **without resetting the env processors**. The
counter therefore ran continuously ACROSS episodes: unless an episode's length
was a multiple of `n_action_steps`, every episode after the first
reconstructed its first targets against an anchor captured mid-chunk —
initially one from the *previous episode's* scene.

Why every prior check missed it: training loss is eval-independent; the unit
tests used single-episode synthetic values; and the `gt-replay` **gate** runs
at `n_action_steps=1`, where every step is a chunk start so the leak is
invisible. It only bites at the policy's real `n_action_steps` (>1), from
episode 2 onward — i.e. exactly in closed-loop eval, and nowhere cheaper.

**Fix:** `reset_episode_state()` on both stateful steps (clears `_call_count`,
`_chunk_anchor`, and the seq accumulator `_running_target`), invoked at every
episode start via a `rollout` wrapper in `eval_libero_ee` and directly in
`eval_replay`. GT-replay of `world-n0` at `n_action_steps=100`: **20% → 80%**.
Regression tests: `test_libero_processor.py::test_bug5_*`.

**Corrected closed-loop eval** — same checkpoints, re-evaluated in ~1 min each
(this is what `anvil-sim-bench run <spec> --from-stage eval --force-stage eval`
is for; note `--force-stage eval` was itself fixed this session to actually
drop the cached `eval_info.json` instead of silently reusing it):

| Condition (task10, ACT) | Broken eval | Fixed eval |
|---|---|---|
| `goal-world-n0` | 40% | **80%** |
| `goal-hand-n0` | 30% | **80%** |
| `goal-world-seq` | 10% | **50%** |
| `goal-hand-seq` | 10% | **30%** |
| `ee-rel` | 10% | **30%** |

`goal-abs` (100%), `native`, `native_rot6d`, `ee_abs`, `ee_delta` are not
chunk-anchored and were unaffected. Net: `world-n0`/`hand-n0` reach native
parity (80%); anchor-relative re-encoding is not the penalty Experiment 8
reported, though plain `goal-abs` still leads on this task.

### Experiment 3c: task11 rotation-heavy robustness contrast

Is `goal-abs`'s task10 dominance task-independent? Tested on `task_index=11`
"put the wine bottle on the rack" (`libero_goal` `task_id=9`, rotation RMS
0.0258 ≈ 3.1× task10's), running `native` / `native_rot6d` / `goal-abs`
end-to-end through the harness with zero hand-written scripts — also the
harness's end-to-end acceptance on a brand-new task (fresh convert, new-task
replay baseline, 50k train, eval, ledger).

| Condition (task11, ACT, n=10) | pc_success |
|---|---|
| `native` | **80%** |
| `native_rot6d` | 70% |
| `goal-abs` | 70% |

**`goal-abs`'s dominance does NOT transfer:** on the rotation-heavy task it
trails `native` (70% vs 80%). Across both tasks `native` is the most reliable
representation; `goal-abs` is competitive-to-best on rotation-light task10 but
not robustly superior. Exactly the task-dependence the n=10 caveat warns
about — and the reason the harness exists.

### Real bug #1 (fixed): `ee_rel` chunk-anchor mismatch

`ACTPolicy`/`DiffusionPolicy.select_action()` only calls the model every
`n_action_steps` calls (internal action queue); the other calls just pop a
cached action without looking at the current observation. `ee_rel`'s
`ee_rel_inverse` reference must be the observation from when that action's
*chunk* was generated, not the fresh observation at the time it's
individually executed — otherwise the reference silently drifts worse and
worse within each chunk. Fixed in `AnvilEEActionProcessorStep` by tracking
the chunk boundary via a call counter synced to `n_action_steps` (which is
read dynamically from the loaded policy's own config — same mechanism for
ACT and Diffusion, verified from their `modeling_*.py` source). Regression
test: `test_ee_rel_action_uses_chunk_start_anchor_not_fresh_observation`.

### Real bug #2 (fixed): `ee_rel` double-relativization

`libero_convert.py` used to pre-relativize the `libero-task10-rel` dataset's
`action` column via `ee_rel_forward` at write time. But `anvil-trainer
--action-type=ee_rel`'s `EERelTransform` *always* relativizes whatever
`action` it loads, on the assumption the dataset stores absolute values (the
same absolute dataset is meant to serve both `--action-type=ee_abs` and
`ee_rel` — that's the whole point of the flag, matching how real MCAP-derived
datasets work). The result: `ee_rel`'s training targets were relativized
*twice*, corrupting them completely while still leaving a deceptively normal
training loss (0.018, essentially identical to `ee_abs`'s 0.019) — closed-loop
success was 0% regardless of step count. Fixed by having `libero_convert.py`
write the same absolute action into both the `abs` and `rel` datasets (they
are now byte-identical in content, differing only by directory/repo name);
relativization happens exactly once, at `anvil-trainer` load time. Regression
test: `test_libero_convert.py::test_convert_episode_actions_returns_absolute_not_relative`.

### Real bug #3 (fixed): `native` + Diffusion Policy training crash — `lerobot` upstream bug

`lerobot-train --dataset.repo_id=lerobot/libero --dataset.episodes=[...]
--policy.type=diffusion` crashed with `IndexError: Invalid key: 133425 is
out of bounds for size 4563` inside the DataLoader. Root-caused (confirmed
via two isolated repros with plain, unmodified `lerobot-train` — not
anvil-trainer, since `native` never goes through it) to a real `lerobot`
library bug: `lerobot/scripts/lerobot_train.py` builds an `EpisodeAwareSampler`
for any policy with a `drop_n_last_frames` attribute (Diffusion, VQ-BeT,
etc. — ACT has none, which is why `native` + ACT worked fine against the Hub
dataset directly). That sampler's indices come from
`dataset.meta.episodes["dataset_from_index"/"dataset_to_index"]` — GLOBAL
absolute frame indices across the *full*, unfiltered Hub dataset (metadata
isn't filtered by `--dataset.episodes`). But `LeRobotDataset.__getitem__`
expects an index *relative* to the filtered `hf_dataset`. Filtered + a
sampler-requiring policy crashes; unfiltered works fine (confirmed both
ways). Fixed the same way as B/C: `libero_convert.py`'s `_make_native_dataset`
writes a LOCAL, unfiltered-at-load-time copy of `native`'s own 8-dim/7-dim
schema (plain `LeRobotDataset.create()`, no Anvil code at all) so no
Hub-side filtering is ever needed. One thing to watch: this local dataset's
camera keys must stay `observation.images.image`/`image2` (the *live* env's
own names) — `native` has no custom eval-time processor to rename them back,
unlike B/C's `AnvilEEObsProcessorStep`. Getting this wrong (briefly, while
fixing the sampler bug) breaks `lerobot-eval`'s
`validate_visual_features_consistency()` with a `Missing/Extra features`
error.

## Modules

- `libero_convert.py` (`anvil-libero-convert`): filters `lerobot/libero` to
  one task and writes the native/native_rot6d/ee_abs/ee_rel/ee_delta
  comparison datasets; also calibrates robosuite's native delta scale/frame
  convention from real data.
- `libero_processor.py`: `AnvilEEObsProcessorStep` / `AnvilEEActionProcessorStep`
  — the format-conversion `ProcessorStep`s used by arms B/C (and experiment
  4, `ee_delta`), including the chunk-anchor tracking described above.
  Also `NativeRot6dActionProcessorStep` for experiment 5, which needs no
  paired obs processor at all.
- `eval_libero_ee.py` (`anvil-eval-libero`): closed-loop eval driver for
  B/C/`ee_delta`, built on the native `LiberoEnv` + `lerobot_eval.rollout()`.
- `eval_native_rot6d.py` (`anvil-eval-native-rot6d`): closed-loop eval driver
  for experiment 5 — reuses lerobot's own stock `LiberoProcessorStep` for
  observations (unlike the above, no Anvil-specific obs encoding needed) and
  only swaps in the custom action decoder.
